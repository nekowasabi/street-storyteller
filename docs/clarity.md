# Clarity（わかりやすさ）の設計

この文書は、street-storyteller に Clarity という性質を足す理由と、その形を決めた経緯を説明する。用語は [用語集](glossary.md) に従う。型と検査はまだコードに無い。2026-11-07 時点の設計である。

## 何を解きたいか

読者が物語を追えなくなる瞬間を、原稿を出す前に機械で見つけたい。

読者が本を閉じる原因のうち、「面白くない」より手前に「分からない」がある。場面を読むのに要る事実や前提を、読者がまだ受け取っていない、または受け取ったが結びつけられない。この時点で読者はサスペンスを感じる前に離脱する。面白さは、理解できたあとにしか評価されない。

今の street-storyteller は、参照先のエンティティが存在するかを `meta check` と `lsp validate` で確かめる。伏線や情報が意図どおりの順序で並んでいるかは、作者の記憶と目視でしか確かめられない。書き直すたびに全部読み返さないと安心できない。テストが無いコードをリファクタするのと同じ状態である。

Clarity は、この「前提が揃っているか」だけを切り出して宣言と検査の対象にする。

## Clarity の定義

Clarity は、各章を読むのに要る前提が、提示順でそれより前の章で読者に渡っていること。

面白さ、サスペンス、好奇心とは別の軸である。研究整理の文書（2026-11-07）も、わかりやすさ（因果・目標・状況を読者が組み立てられること）、読みやすさ（語や文の処理のしやすさ）、面白さ（サスペンス、好奇心、驚き）を分け、1 つの点数にまとめるなと述べている。Clarity はこのうち「わかりやすさ」に当たり、面白さの前提条件として置く。

「読者の期待値」もこの定義の中で扱う。ここでの期待値はサスペンスではなく、「読者がこの先を読むために持っていてほしい前提」である。たとえば「第 3 章に入る時点で、読者は鍵が店主の手元にあると信じている」は、面白さではなく、第 3 章が理解できるための条件である。

## 機械が確かめられる範囲

コードで確かめられるのは構造の条件まで。宣言した前提が提示順で揃っているかは落とせる。読者が実際に結びつけられたかは、人の読者実験でしか分からない。

研究整理の文書は、警告を「合否ではなく候補」として出し点数化しないよう勧めている。設計比較の文書も「総合点を付けない」と書く。一方、この設計の出発点は「通らなければコンパイルエラー」である。両立させるために、検査を 2 種に分ける。

- 硬く落とす。参照の存在、前提の提示順、訂正の系譜、番号の重複。構造の条件で、機械が判定できる。
- 候補として出す。読者が実際に理解し期待したか。人の読者実験でしか確かめられない。

出口のゲートが保証するのは「宣言した意図と原稿の構造が一致している」ことまでで、「わかりやすい」ことではない。

## 意図した謎と意図しない欠落を分ける

同じ物語で「分かりやすい版」「謎の版」「欠落の版」を比べると、物語内の真実は同じで、開示と意図の記録だけが違う。だから物語内の真実と読者への開示を別の層で持たないと、意図した謎と意図しない欠落を区別できない。

Clarity では、伏せたい命題を `withheld` と宣言する。宣言のある未開示は通り、宣言の無い未開示だけが落ちる。誤信させたい命題は `may-remain-misled` と宣言すれば、誤信のまま終えてよい。

## どこに置くか

設計比較の文書は 2 案を比べた。

- 案 A。Beat の任意欄を拡張し、出来事と読者への提示を同じ場所に書く。編集の手間が小さい。
- 案 B。読者理解を独立したファイルに置き、Beat は変えない。世界の出来事と読者への提示を別の変更単位にできる。

最初は案 A を推した。編集の手間が勝つと見たからである。この判断は撤回した。Beat は「何が起きるか」の単位で、物語内の真実の記録である。Clarity は「読者がここまでに何を受け取っているか」で、読者が読む順序の上に乗る。提示順を持つのは Beat ではなく章である。Beat を回想で入れ替えても Beat は変わらず、変わるのは章の並びである。出来事と提示を同じ型に書くと、この 2 つが混ざる。

決めた構造は次のとおり。

### Proposition は新しい要素種別

`src/propositions/` に置き、Go は `internal/domain/proposition.go`。`propositionId`、`statement`、`authorTruth`、`resolutionPolicy` を持つ。`internal/project/project.go` の種別一覧（character、setting、foreshadowing、timeline、plot）に 6 つ目として足す。ディレクトリが無ければ読み飛ばす。Beat や Event への参照は任意で、必須にしない。

### Disclosure と Requires は原稿の frontmatter

原稿の frontmatter に `reader_shows`（Proposition と Stance の組の列）と `reader_requires`（同じ組の集合）を足す。既存の `characters` や `foreshadowings` と同じ並びである。置き場所が原稿なのは、読者が読む順序を持つのが原稿だからである。`manuscript_binding` ツールと `meta annotate` が同じ欄を扱える。`PlotBeat` の型は変えない。

### 検査はサービス 1 つ

`internal/service/` に `ReaderPrereqService` を足す。原稿を章の順に走査し、次を見る。

| 名前 | 規則 |
|---|---|
| RDR-102 前提 | `reader_requires` の各組が、提示順でより前の `reader_shows` に在る |
| RDR-103 訂正 | `corrected` は、同じ命題の `misled` がより前に在る |
| RDR-104 方針 | `must-correct-if-false` の命題は、最終章で `corrected` |

走査は `MetaCheckService` と同じ深さ 1 で、CLI と MCP の両方から呼ぶ。

### 出口は 2 つ

`storyteller meta check` が `manuscripts/` に対して `ReaderPrereqService` を走らせ、落ちたら終了コード 1 で返す。MCP の `meta_check` も同じ違反を返す。

加えて `storyteller manuscript build` を `internal/cli/modules/` に足す。今のリポジトリに draft から manuscript への出力コマンドは無く、`drafts/` は雛形生成と `meta check` の除外にだけ出てくる。`build` は `drafts/` の原稿を同じ検査にかけ、通れば `manuscripts/` へ写し、落ちたら 1 ファイルも書かない。これが「コンパイル」に当たる。

## 形式検証

検査が信用できることを、実装の前に TLA+ で確かめた。モデルと走らせ方は `.claude/skills/verify-reader-prereq/` にある。

架空の物語「雨夜の鍵」（4 章、3 命題）に対して 3 規則を全経路検査した。本編は 3 規則すべて成立。ch-03 を ch-02 より前に置く別案では、RDR-102 が 2 手で破れる。モデルの写しに 5 通りの壊し（ch-02 の開示を消す、ch-04 の `misled` を消す、ch-04 の `corrected` を消す、ch-04 の列を逆転する、ch-02 の `withheld` の宣言を消す）を入れ、それぞれ対応する規則が落ちることを確かめた。

モデルを書く途中で、スケッチの 04 に `misled` が無く `corrected` だけがあるのを RDR-103 が拾った。検査が設計データの誤りを見つけた最初の例である。

モデルの読む単位は章で、スケッチの `manuscripts` を写している。最初は Beat 単位で書き、構造を章に変えたときに書き直した。規則と結果は変わっていない。

## 研究と資料の位置づけ

Clarity の定義は、物語理解の実証研究（Trabasso と van den Broek 1985、Graesser ほか 1994、Zwaan と Radvansky 1998 の系統）に沿う。読者の理解を因果のつながり、状況モデルの更新、参照の解決、目標推論として扱う枠組みである。

処理流暢性の研究（Laham、Koval、Alter 2012）は、読みにくいと好感と信頼が下がることを示す。対象は名前やフォントで、物語の前提の直接の根拠ではない。「理解の負荷が高いと対象を避ける」という機構の裏付けとして引く。

Dラボの関連回（Q&A89、超記憶力#2、モナシュ大学教授との対談）は、流暢性と離脱の関係、物語形式が因果でつながると理解しやすいことを紹介している。一次研究ではなく紹介の中の要約なので、「なぜこの概念を置くか」の説明に添える位置づけとする。

## 決めたこと（2026-11-07）

- 章の順序は `manuscripts/` のファイル名順。順序を明示する欄は足さない。
- `reader_requires` の Stance は null にできる。null は、その命題が何らかの態度（`withheld` を含む）で開示されていればよい。脇役のように動機を持たない人物について、読者に態度を求めずに「触れてある」ことだけを前提にするために使う。
- 同じ章の `reader_shows` の列の中の順序も検査する。RDR-103 は前の章か、同じ章の列でより前の `misled` を見る。
- 複数 plot と回想は範囲内。どちらも章の順にしか影響しないので、Clarity の検査に plot と Event は要らない。回想は章の並びとして扱う。
- frontmatter の書式は文字列リスト。`reader_shows: ["loc:shown", "hist:withheld"]`、`reader_requires: ["loc:shown", "hist"]`。既存の frontmatter 解析はスカラーと文字列リストしか読まないので、オブジェクトの列にはしない。
- frontmatter の `order` 欄は提示順に使わない。
- 出口は 2 つ。`storyteller meta check` に Clarity 検査を足し、`storyteller manuscript build` が `drafts/` を検査して `manuscripts/` に写す。落ちたら写さない。
- 落ちたときの出力は違反ごとに 1 行 `ファイル:行 RDR-10x 説明`。`--json` では既存の形に違反の配列を入れる。
- LSP で `reader_shows` / `reader_requires` の値（命題 ID と態度）を補完できるようにする。

実装の検証項目は `.claude/skills/verify-clarity-impl/SKILL.md` にある。

## 決まっていないこと

- `docs/plot.md` は `preconditionBeatIds` の循環参照を DFS で検出すると書いているが、`internal/` にその実装は無い。文書を直すか実装するかは未決である。Clarity とは別の問題だが、同じ検査の層に入る。
